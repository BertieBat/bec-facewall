# FaceWall security hardening — deployment checklist (November 2026)

GitHub Actions runs PHP lint and mocked regression tests; it **cannot** query
your live CiviCRM schema or protect uploaded files already on the server.

## Privacy change

All FaceWall public views now require the custom field
custom_value_1_BEC.facewall_public_84 = 1 (affirmative FaceWall Public consent).
Missing or unrecognised values are treated as not public. This includes current,
joint (both parties), probationary, under-30, historical members, officer
displays, and PDF posters.

**Before deployment**, verify that 1 is the club's intended consent setting
and compare how many members have this value. The previous FaceWall main
member grid displayed a member's photo only when the field was 1.

The stored historical tables remain internal reporting tables, while public
shortcodes join against live consent on every read.

## Safe rollout

1. Back up the WordPress plugin directory and CiviCRM database. Deploy the
   updated plugin to a staging WordPress/CiviCRM site first.
2. Review current, probationary, under-30, joint (both sections), grace,
   LYBNTY, life, historical, officers and member-list shortcodes. Compare
   totals against consent data, and verify opted-out people are excluded.
3. In the administrator menu, visit FaceWall → A1/RA1/SRA1 Poster and use
   the new download link. The resulting PDF should contain opted-in members
   only and should **not** be saved under the plugin directory.
4. Refresh Joint Members several times. There must be no TRUNCATE or write
   to CiviCRM's relationship cache on a page request. If that cache is
   incomplete, use CiviCRM's own supported maintenance tools.
5. Trigger the WordPress event named facewall_cron once from scheduled-job
   administration. Check the site's PHP error log for Facewall cron entries.
   The plugin no longer writes facewall_cron.txt in its own directory.
6. Check image previews, original CiviCRM PNG/JPG photographs, and stale
   thumbnails. Missing thumbnails now show a placeholder to visitors;
   eligible images are generated by the maintenance job.
7. Examine PHP error logs and then deploy the staging-tested plugin live.

## Host-side cleanup

The plugin's .htaccess blocks direct access to PHP/PDF/TXT/log files on
Apache 2.4+. Nginx requires equivalent web-server configuration.

Check the LIVE SERVER for old files, then safely remove:

- wp-content/plugins/facewall/zzpluralzalpha/ — obsolete Mailman files.
- wp-content/plugins/facewall/facewall_cron.txt — old log.
- wp-content/plugins/facewall/poster_output/*.pdf — previously generated PDFs.

Do NOT delete wp-content/uploads/civicrm/custom; CiviCRM uses it for actual
member photos. Consent protection limits what FaceWall outputs, but does not
itself revoke public access to original image URLs. Review CiviCRM upload
permissions and any previously published image URLs separately.

## Tests

From the plugin root:

    find . -maxdepth 2 -name '*.php' -print0 | xargs -0 -n1 php -l
    php tests/facewall-regression.php
    php tests/joint-membership-regression.php
    php tests/facewall-security-regression.php

These are mock tests, not a live CiviCRM integration test.

## Remaining maintenance risks

The scheduled historical reporting rebuilds still use TRUNCATE then INSERT.
They are protected by a concurrency lock and source preflight, but are NOT
atomic: a database failure may leave partially repopulated reporting tables.
Rollback to the old plugin also restores its previous security issues.
